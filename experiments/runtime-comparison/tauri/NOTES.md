# macOS Tauri comparison shell

This isolated macOS 14+ executable loads the production frontend from the shared runtime-comparison server and uses its common Node backend and bridge. It does not implement a Rust business-logic backend. Tauri 2.12.5 and the dependency graph are locked in `Cargo.lock`. The comparison prototype is separate from the deployed app; see [the comparison methodology](../NOTES.md) for the workload, analysis, and limits.

The comparison build script packages the release binary into an ad-hoc-signed, background-only `.app` under `artifacts/runtime-comparison`. The runner launches that bundle through macOS LaunchServices (`open -n -g -W`) with its environment and captures stdout/stderr. LaunchServices is required for the intended responsibility identity: launching the raw binary directly can leave launchd-hosted WebKit XPC services attributed to another process. The sampler adds only same-UID WebKit XPC processes whose responsible PID exactly matches a process in the selected runtime tree, and the runner requires a WebContent process at every measured snapshot. The responsibility lookup is private and best effort; this does not prove complete attribution of short-lived or otherwise unattributed work.

The shell starts under AppKit's prohibited activation policy, then switches to accessory after Tao's launch callback. It creates the window hidden, nonfocusable, and non-key, ignores mouse events, sets its native window level to -1, and uses `orderBack` to put it behind the user's windows. It checks activation policy, window capabilities, visibility, and inactivity around ordering; an unexpected focus event ends the process. The common sampler checks the frontmost PID during measured phases. These safeguards are designed for Stage Manager and keeping the user's work undisturbed, but a periodic PID check cannot prove that activation never occurred between samples, and an external activation request is outside the shell's control.

The window uses a nonpersistent WebKit data store and `BackgroundThrottlingPolicy::Disabled`, which selects WebKit's public inactive scheduling policy on macOS 14+. Full Stage Manager occlusion still stopped RAF on the measured host, so this experiment also requires the private `_setWindowOcclusionDetectionEnabled:NO` WebKit SPI and reports its use at readiness. This is isolated experimental scheduling control, not a production recommendation. The shared test page simulates `document.visibilityState = 'visible'` equally in both shells and retains native visibility observations separately. These controls do not prove unoccluded display or remove all system scheduling effects. The shell requests the native WebKit view with default hardware acceleration; per-process CPU energy is measured where available, but GPU, display, and total application/device energy are not attributed. RAF/DOM acknowledgement is not a measurement of physical presentation.

HTTP remains the default bridge. Opt-in native mode uses authenticated persistent Unix-domain JSON frames and Tauri invoke/Channel, preserving the common Node backend and application payloads. Frames are bounded at 128 MiB; startup chart-universe payloads exceed the original 20 MiB experimental bound. The exact loaded page alone receives the experimental command permissions. This uses the pinned, unstable `runtime_authority_mut().__allow_command` API and requires review if Tauri is upgraded; it is not a reusable production permission design. Raw payloads still incur native SDK serialization/copying, so the native/HTTP contrast measures the whole path replacement.

The shell validates a numeric loopback URL and positive logical window dimensions; the runner requests 1200 × 760 logical pixels. Its readiness JSON describes native window creation, actual physical inner size, scale factor, and focus/visibility state. It does not itself mean that the frontend or the workload has completed. A direct standalone invocation is not the formal measured launch path.
